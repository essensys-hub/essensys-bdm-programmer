Guide dédié · Raspberry Pi Pico (RP2040)

Pico → BDM SC944D : câblage, Mac, flash firmware

Procédure complète : lever l’ambiguïté TCLK, brancher le Pico sur J33 (schémas type Fritzing), flasher le firmware Pico, parler au Mac en USB CDC (chemin principal) ou UART (debug optionnel), puis exporter / uploader le firmware cible via le pipeline BDM.

01 Lever TCLK (NC)
02 Câbler Pico ↔ J33
03 Flasher le Pico (UF2)
04 Mac ↔ Pico (USB / UART)
05 Backup / program / verify

00 Prérequis & sécurité

STOP
Avant tout fil :
  • Carte SC944D alimentée en 3,3 V (logique Pico = 3,3 V — pas de 5 V sur les GPIO).
  • Jumper JC1 monté → mode BDM (sinon J33 est en JTAG). À VÉRIFIER
  • Relier GND en premier, retirer GND en dernier.
  • Ne jamais injecter de courant dans +3V3S (broche 7) — sense uniquement.
  • Résistances série 100–330 Ω recommandées sur DSCLK/DSI/DSO ; buffer 74LVC idéal.
  • Matériel : Pico (ou Pico W), câble USB-A/C → micro-USB, fils Dupont, connecteur 2×5 vers J33.
  • Mac : macOS avec accès série (/dev/cu.usbmodem* pour CDC).
  • Schémas : vues type Fritzing (breadboard SVG). Recréables dans Fritzing depuis les tables de broches.

01 Lever l’ambiguïté — J33 broche 1 TCLK

DÉCISION
Broche 1 TCLK = NC (non connectée). Ne pas la brancher au Pico. Le protocole BDM série 3 fils (DSCLK / DSI / DSO) n’utilise pas TCLK ; l’horloge du protocole est DSCLK générée par le Pico (maître), cadencée côté MCU sur PSTCLK.

Pourquoi l’ambiguïté ? Sur le schéma SC944D, J33 pin 1 est câblé en UC_TCLK pour compatibilité JTAG / pods legacy. En mode BDM (JC1 monté), ce signal n’entre pas dans le transfert série 17 bits. Le laisser flottant côté pod évite toute injection parasite.

03 Programmer le Pico (firmware pont BDM)

Le Pico n’exécute pas le pipeline métier (SREC, interlocks) : il est un pod. Son firmware fait le timing BDM (PIO) et expose une liaison hôte.

Rôle du firmware Pico

  • PIO : bit-bang déterministe DSCLK/DSI/DSO (paquets 17 bits MSB-first, RM §33).
  • GPIO : BKPT, RESET open-drain, lecture ALLPST / +3V3S.
  • USB CDC principal : port série virtuel — commandes texte/binaires depuis le Mac.
  • UART optionnel : même flux de commandes sur GP0 (TX) / GP1 (RX) pour debug.
Fritzing · étape 3 — flasher le UF2 (BOOTSEL)
  1. Débrancher le Pico du BDM si besoin (sécurité).
  2. Maintenir BOOTSEL, brancher USB au Mac, relâcher → volume RPI-RP2.
  3. Copier le fichier *.uf2 du firmware pont → le Pico redémarre seul.
  4. Sans BOOTSEL, le même câble USB sert ensuite de CDC (étape 04).
# Après flash (CDC actif), le Mac voit typiquement :
ls /dev/cu.usbmodem*

# Contenu logique du firmware (contrat) :
# - CDC (et UART optionnel) : commandes ping | info | read | write | reset | halt
# - PIO : trames BDM 17 bits ; DSCLK maître
# - Interlocks flash CFM restent côté CLI Mac, pas dans le Pico

04 Connecter le Pico au Mac

Chemin principal — USB CDC recommandé

Un seul câble USB : alimentation + flash UF2 + port série virtuel. Aucun dongle UART.

Fritzing · étape 4a — Mac ↔ Pico USB CDC (et Pico déjà câblé J33)
# macOS — ouvrir le port CDC (exemple)
screen /dev/cu.usbmodem* 115200
# ou :  minicom -D /dev/cu.usbmodem* -b 115200
# ou CLI projet :  essensys-bdm --transport pico-cdc --port /dev/cu.usbmodemXXXX

Fritzing · étape 4b — Mac ↔ USB-UART ↔ Pico (GP0/GP1) + BDM inchangé
C
CDC = défaut. UART = second canal debug. Ne pas brancher CDC et UART en même temps sur deux outils qui écrivent des commandes concurrentes vers le même moteur BDM.

05 Exporter / uploader le firmware cible

Le Mac exécute le CLI essensys-bdm (ou équivalent). Le Pico transporte seulement les accès mémoire BDM. Pipeline sûr (interlocks) :

1 · info Identité / +3V3S / halt
2 · backup Dump flash → fichier + sha256
3 · program Zone app seulement
4 · verify Relire + comparer
5 · reset Relancer la cible
Fritzing · étape 5 — flux données firmware (export / upload)
# Exemple de session (CDC) — noms CLI indicatifs
essensys-bdm --transport pico-cdc --port /dev/cu.usbmodemXXXX info
essensys-bdm --transport pico-cdc --port /dev/cu.usbmodemXXXX backup -o backup-$(date +%Y%m%d).bin
essensys-bdm --transport pico-cdc --port /dev/cu.usbmodemXXXX program firmware-app.srec \
  --backup-record backup-….json
essensys-bdm --transport pico-cdc --port /dev/cu.usbmodemXXXX verify firmware-app.srec
essensys-bdm --transport pico-cdc --port /dev/cu.usbmodemXXXX reset

# Export = backup (lecture flash → fichier hôte)
# Upload = program + verify (écriture zone application uniquement)
CFM
Toute écriture dans 0x400–0x417 (Security Word inclus) est interdite par les interlocks — risque de couper le BDM à jamais. Le Pico doit refuser / le CLI doit bloquer avant WRITE.

06 Checklist rapide

  1. JC1 = BDM ; J33-1 TCLK non câblé.
  2. GND commun ; mapping GP2–GP8 ; RESET en open-drain ; +3V3S en sense.
  3. UF2 flasheé (BOOTSEL) → firmware pont PIO + CDC.
  4. Mac : /dev/cu.usbmodem* (CDC) ; UART GP0/1 seulement si debug.
  5. info → backup → program → verify → reset ; jamais sans backup vérifié.
